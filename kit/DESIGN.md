# Lab kit design

**Invariant:** tests run in a fixed priority order (phases 1-8), and every planned step ends with exactly one recorded outcome (`ok`, `skipped` + reason, `absent` + reason, `failed`, `timeout`, `interrupted` or `crashed`), and its raw output sits next to it. Nothing is silently dropped, and the kit never changes the lab machine beyond `/var/tmp/perseus-kit-local` and the page-cache drop in the one `sudo` test.

| Exit | Behaviour | Test |
|---|---|---|
| done | `status=ok`; summary.txt + `FINISHED` marker written | local e2e run |
| failed | `status=failed`, exit code in `status.json`, stderr kept; run continues with the next step | e2e: corrupted model copy fails its stage step |
| skipped | `status=skipped` + reason (single NUMA node, no sudo, not enough RAM, model not on USB) | e2e on this 1-node box |
| timeout | `timeout` exit 124/137 → `status=timeout` | untested (see Known gaps) |
| cancelled (Ctrl-C) | the signal reaches the benchmark itself (`timeout --foreground`, same process group), current step → `interrupted`, summary written, lock released, exit 130 within seconds; rerun repeats that step | e2e: SIGINT to the process group mid-bench; stops < 20 s, no `llama-*` left |
| terminal closed (SIGHUP) | same as Ctrl-C | shares the trap; not separately tested |
| crash / power loss / OOM kill mid-step | `started` marker without status → next run marks it `crashed` and does **not** retry it (so one bad step can't wedge every rerun); `--retry-failed` reruns it. A dead runner left as a zombie doesn't hold the lock | e2e: kill -9 the process group mid-step, with and without an init reaping zombies |
| retried | `--retry-failed` reruns failed/timeout/crashed; ok/skipped never rerun | e2e |
| duplicated (two runs at once) | `mkdir` lock with host+pid; live owner → refuse; stale owner → atomic `mv` takeover, one winner | e2e: second run while first is live |
| paused (`run.sh pause`) | flag file; the runner finishes the current test, then stops cleanly (exit 0, summary written); a stage step waiting on the copier ends `interrupted` and reruns | e2e: pause mid-bench |
| stopped (`run.sh stop`) | SIGINT to the runner's process group (recorded in the lock) = Ctrl-C | e2e |
| time limit (`--for TIME`) | no new test starts after TIME (`95` = minutes, `90m`, `8h`, `1h30m`; 0, empty, fractions and over a week are usage errors, exit 2) (uptime clock, immune to a wrong wall clock); the running one finishes; the banner's cutoff is that deadline, not one counted from after setup | e2e with `--for 1`; e2e-tty (a) parses each form |
| screen (`lib/ui.sh`) | run.log always gets the plain lines. A terminal gets phase rules, a glyph and `[n/total]` per step, and a live timer: a background subshell redrawing the running step's line each second. The runner kills it when the step ends and in the Ctrl-C/stop trap before printing "Stopped." (the stopped step keeps its line); it polls the runner's pid and state, so a kill -9 of the runner alone ends it within a second even while the runner is an unreaped zombie. Builtins only, one `sleep` a second, since it shares the box with benchmarks. No timer on a terminal narrower than its line (a wrapped redraw leaves a trail) or TERM=dumb; on a resize (SIGWINCH) the width is re-read (`stty size </dev/tty`), a running timer that no longer fits clears its line and stops, and the next step re-checks; colour only without NO_COLOR and TERM=dumb; ASCII glyphs outside UTF-8 locales; a pipe or file gets the plain lines | e2e-tty: pty runs (colour, NO_COLOR, LANG=C, 40 columns, narrowed to 40 mid-step, setup slower than --for), pipe, status mid-step, stop mid-step (no redraw after "Stopped.", nothing left), kill -9 of the runner alone, and under a parent that never reaps it |
| background copy | copier in its own session at idle CPU/IO priority (the runner records its pid before any step runs, so a stage step never copies alongside a copier that hasn't started yet), copies in plan order, sha256 → `.ok`/`.bad`/`.nospace`; killed with the runner; a copier orphaned by a crash is killed on the next start and its `.part` removed; each bench records whether a copy was running (`env.txt`) | e2e: copy mode, stop mid-copy, kill -9 mid-copy; e2e-diag (b): copier delayed 3 s at start, the resumed run's first stage step waits for it |
| reordered | steps have fixed ids; resume keys on the id, not position | by construction |
| USB moved to another machine | lock owner host differs → treated as stale; results dir is per host | by construction |
| identity change (sudo vs not) | local cache path fixed (`/var/tmp`), not `$HOME` | by construction |
| wrong CPU build | variant picked from `/proc/cpuinfo` (or forced with `PERSEUS_VARIANT`, validated), then proven with a tiny real benchmark; SIGILL → next older build | QEMU (`build-kit.sh test`): emulator traps each newer extension, each build runs every shipped kernel on its oldest target CPU, a newer build traps. The step-down loop itself is untested |
| perseus kernels wrong on the real CPU | steps 2-00 (SSSE3, multi-column and repacked-IQ3_S kernels), 2-00b (tiled matmul), 2-00d (IQ3_S repack through ggml's graph API) and 2-00f (Flash-Next formats q6_K/q5_K/iq4_nl/q2_0, plus q4_1) run the self-tests on the lab box first; a failure is recorded like any step, so Saluki (2-00..2-00d) or Qwen3.8-27B (2-00f: its q6_K/q5_K/q4_1 tensors) numbers after it are known-suspect | `kernels/test_ssse3_kernels.c`, `kernels/test_fn_kernels.c` (both mutation-tested), llama.cpp's `test-tiled-mulmat`, `kernels/test_repack_mulmat.c` (fails when the repack is off), QEMU Penryn/Nehalem |
| repacked weights use more RAM than the file | IQ3_S tensors grow 31% at load (Saluki +0.39 GB, 5%); `ram_check` keeps a 15% + 1.5 GB margin over the file size | by arithmetic |
| A/B steps (7-08 multi-column off, 8-14 tiled off, 8-19 repack off) | the step exports `PERSEUS_MC=0` / `GGML_CPU_TILED_MM=0` / `PERSEUS_REPACK=0` inside its own subshell, so later steps never inherit it; `env.txt` records the overrides; a malformed `PERSEUS_MC` / `PERSEUS_REPACK` aborts instead of silently defaulting | `PERSEUS_MC=off` aborts; with `PERSEUS_MC=0` the self-test fails (the switch works); MTP output identical with it on and off |
| model not on this USB (diag kit; core kit's standard-tier models) | `status=absent` + reason. Not final: every resume re-evaluates it, so a USB re-assembled with a bigger tier runs it. Only the USB counts (a local copy from an earlier, bigger kit doesn't), so a diag kit never runs model tests. `status` counts them per phase ("need models not on this USB"); summary.txt lists each one plus their total | `kit/test/e2e-diag.sh` (b): diag run paused after 2-05, USB re-assembled with core, resume runs 2-01..2-05. Fails when `absent` is final like `skipped` |
| diag kit (no models) | phases 1-3 run (the GPU checks need no model); every model step ends `absent`; FINISHED and DONE (with the absent count); no background copier and nothing in the local dir but `bin/`; the startup line says diagnostics-only, ~10 min. With no tiny model, one trial of the kernel self-test proves the CPU build instead of a tiny benchmark | e2e-diag (a), on a FAT32 image mounted by `udisksctl` |
| USB re-assembled after a FINISHED run | FINISHED is final: the next run starts a new results folder and repeats phases 1-3 (~15 min) before the model tests | by construction (`pick_run_dir`) |
| FAT32 USB | `assemble` refuses it for core/standard (files over 4 GB) and allows diag. udisks mounts vfat with `showexec` (udisks2 2.11.2's builtin `vfat_defaults=uid=$UID,gid=$GID,shortname=mixed,utf8=1,showexec,flush`), so nothing on the stick is executable (exec gives 126, chmod is a no-op); run.sh only executes its local copy of `bin/` | e2e-diag (a) on a FAT32 image mounted by `udisksctl` |
| damaged model copy | sha256 checked after copying to local disk; mismatch → `.bad`, model steps skip | e2e: one flipped byte in the USB copy |
| RAM too small for a model | skipped with the numbers, never started (avoids OOM-killing the box) | e2e-gpu: Flash-Next (75.8 GB) on a box with less free RAM |
| hidden memory use beyond the weights | completion/MTP steps pass `-c` (default is the trained 262k context = ~17 GB KV on Qwen3.8-27B); llama-bench sizes its own context | 27B + MTP head runs in a 12 GB cgroup with `-c 1024`; OOM-killed twice without it |
| USB read-only / full | refuses to start with a message | untested (see Known gaps) |

Copies others hold: the page cache holds model files between steps (deliberate; `distribute-cold` drops it first); `/var/tmp/perseus-kit-local` holds binaries + models until `run.sh clean` (a diag kit puts only `bin/` there). Model copies left there by an earlier kit are not used unless the USB carries that model too.

## GPU (phase 3) and Flash-Next (phase 4)

The lab box has an AMD RX 580 (Polaris, PCI `1002:67df` rev e7). Flash-Next's per-token bytes are mostly its always-read part (attention, shared experts, router: ~3.8 GB/token in the IQ3_XXS build) while its routed experts are ~0.84 GB/token, so the plan is llama.cpp's MoE split: the always-read part on the GPU, routed experts in RAM on the CPU's SSSE3 kernels.

**Invariant:** every GPU step runs on the one device the probe (3-01) picked and names it; no GPU step can make a CPU-only result wrong or missing, and every step still ends with exactly one recorded outcome.

| Exit | Behaviour | Test |
|---|---|---|
| GPU found | 3-01 lists Vulkan devices with the kit's own build and picks the first discrete one (llama.cpp's default list holds only real GPUs, no software rasteriser; of those, the first with `uma: 0`, so an iGPU never counts); records llama.cpp's name for it (`VulkanN`, shape-checked before sourcing) and VRAM in `$RUN_DIR/gpu.env`, its full name in `gpu-name.txt`; every later GPU command selects it with `-dev`/`-b VulkanN`, so a missing device is an error, never a silent CPU run. Not `GGML_VK_VISIBLE_DEVICES`: that indexes Vulkan's raw device list, which can differ from llama.cpp's numbering when a software rasteriser or filtered device comes first | e2e-gpu (a): RX 9070 XT + Ryzen iGPU visible, picks the 9070 XT, bench reports it; (e) with the GPU gone, the old `GGML_VK_VISIBLE_DEVICES=0` selected Mesa's llvmpipe (raw device 0) and its runs passed as GPU results |
| GPU gone or changed after 3-01 (driver removed, device added, resume on another day) | each GPU step re-lists devices (bounded like every command: 120 s, then `timeout`) and fails unless `VulkanN` still has the recorded name. `test-backend-ops` exits 0 when the named backend is missing (it skips it), so its output must show `Backend VulkanN: OK` and more than 0 cases (test) or timed ops (perf), else the step fails | e2e-gpu (e): probe with the GPU, resume without it → 3-02..3-05 `failed`; passed 3-02 on zero cases before this check |
| no usable GPU (no `/dev/dri` access, no amdgpu, no Vulkan driver, only an iGPU) | 3-01 `skipped` with the device list it saw; GPU steps after it `skipped` ("no usable GPU, see 3-01"); Flash-Next CPU-only still runs. sysinfo records PCI ids, VRAM, clocks, render-node permissions and the installed Vulkan drivers, so a missing driver is visible | e2e-gpu (b): no `/dev/dri`; (c): only the iGPU's render node |
| no Vulkan loader on the box | the kit ships the Khronos loader (`libvulkan.so.1`, Ubuntu 24.04) next to the Vulkan binaries (rpath `$ORIGIN/lib`) | e2e-gpu (d): plain Ubuntu 24.04, no `libvulkan1`: the binaries start and list no devices |
| box's glibc older than the Vulkan build's (2.38) | every GPU step `skipped`, naming both versions (`glibc-min` is written at build time from the binaries' symbol versions) | e2e-diag (a), e2e-zip: Debian 12 (2.36) |
| Vulkan build on an older CPU | the Vulkan binaries are the nehalem build only; on a penryn-only CPU every GPU step is `skipped` | by construction |
| GPU computes wrong results | 3-02 replays, on the GPU against the CPU, the ops the tiny model and Flash-Next run (shapes and types exported from their graphs at build time by llama.cpp's `test-export-graph-ops`), plus llama.cpp's own cases for the op types left out (next row); a mismatch → `failed`, and GPU numbers after it are known-suspect (same rule as the CPU kernels). 3-03 (perf) also fails if any case printed llama.cpp's allocation or compute failure: perf mode carries on past them and exits 0 | Polaris-like run on the dev box (`GGML_VK_DISABLE_F16/INTEGER_DOT_PRODUCT/COOPMAT/BFLOAT16/DOT2`): 319/319 Flash-Next ops, 97/97 tiny, 539 built-in TOP_K/SQRT, 367 MUL_MAT_ID; real Flash-Next IQ3_XXS greedy output identical CPU-only vs CPU+GPU (48 tokens) |
| ops a random-input replay can't judge | `kit/build/gpu_ops.py` leaves out classes, not a hand list: index outputs (ARGSORT, TOP_K: tied values come back in another order), ops outside their domain on random inputs (SQRT: NaN on both sides), reductions with under 64 outputs (MUL_MAT, SUM_ROWS: the error becomes relative to a few near-zero random sums), and routed experts (MUL_MAT_ID: they stay in RAM, and quantizing a whole random expert tensor takes minutes per case on the lab CPU). It writes them, with their weight types, to `MODEL.txt.builtin`; 3-02 runs llama.cpp's own cases for exactly those (they use distinct values, compare sets, or valid inputs), so every op type a model uses is checked one way or the other. No op lists in the kit → 3-02 `skipped` | 20 replays of Flash-Next's list on the dev box: ARGSORT (expert routing, 512 per row) and a bf16 2560→1 dot product each failed once with CPU and GPU both healthy; built-in ARGSORT 98/98, SUM_ROWS 10/10, bf16 MUL_MAT 215/215, expert-format MUL_MAT_ID 188/188 |
| GPU too small for the whole always-read part (4 GB card) | Flash-Next CPU+GPU uses llama.cpp's `-fit on`: it fills the GPU back to front with each layer's non-expert weights (experts stay in RAM) until the free VRAM runs out, and spends any surplus on whole expert layers; the decisions are in the step's stderr (`-lv 4`) | dev box: 16 GB card → all 48 layers + 9 layers of experts; ~0.5 GB free → 0 layers, still runs |
| GPU hang / device lost / driver reset mid-step | the process exits non-zero (`failed`) or hangs until its timeout (`timeout`); amdgpu resets the GPU, the lab's screen may blank for a few seconds; later GPU steps run and record whatever happens | untested: no safe way to hang a GPU on purpose (Known gaps) |
| other programs take VRAM during a step | fit measured free VRAM at start; a failed allocation ends the step `failed` | untested (Known gaps) |
| a split model half downloaded at build time | `assemble` exports a model's op list only when every split file is verified (llama.cpp opens them all, even for metadata); otherwise it logs that and goes on | e2e-diag (c): Flash-Next's first file only → diag kit assembles with the tiny model's list |
| Flash-Next's two files | shard 1 (weights, 47.0 GB) and shard 2 (the n-gram table, 28.8 GB, read 16 rows per token) are two catalog rows staged and checksummed like any model; llama.cpp finds shard 2 by name next to shard 1, so a step needs both and needs them in the same folder: one staged locally and the other not → `skipped` with that reason | e2e-gpu: both on the USB with `--no-copy` |
| Flash-Next's size vs RAM and disk | the steps mmap the files (75.8 GB; `-lm none` would hold a second copy beside the page cache); `ram_check` on both shards (needs ~89 GB available; the lab has ~126 GB); the local copy needs 75.8 GB + 5 GB free (the lab has 186 GB) | e2e-gpu: skipped on a 30 GB box |
| copy time | USB 2.0 (~35 MB/s): the copier takes the tiny model, then Flash-Next (~35 min), then the 27Bs; the plan waits at 4-01 until Flash-Next is staged. Phase 3 runs during the copy | by construction (copy order = `PREFETCH_ORDER`) |
| CPU-only vs CPU+GPU A/B | same binary (the Vulkan build), prompt, context, thread count and greedy settings; CPU-only passes `-dev none` (with `-ngl 0` llama.cpp still sends prompt matmuls to the GPU) and `GGML_DISABLE_VULKAN=1`, so Vulkan isn't even loaded and a driver left wedged by a GPU step can't take the CPU baseline down | dev box: `-dev none` + `GGML_DISABLE_VULKAN=1` runs with no Vulkan in its log |
| GPU driver's on-disk shader cache | Mesa keeps compiled shaders under `$HOME/.cache` (`/root/.cache` under sudo); the kit sets `MESA_SHADER_CACHE_DIR` and `XDG_CACHE_HOME` under `/var/tmp/perseus-kit-local/cache`, which `run.sh clean` removes | e2e-gpu (a): nothing appears under `$HOME`, the cache appears in the local dir |

Copies others hold: `$RUN_DIR/gpu.env` holds the picked device for the rest of that run (a resumed run reuses it; a new run probes again). The GPU holds nothing between steps (each step is its own process). Mesa's shader cache under the local dir speeds up later steps' pipeline builds and goes with `run.sh clean`.

## Known gaps
- A step whose command itself exits 3 is recorded as `skipped`: `skip()` and such a command share the exit code. `absent` uses a marker file, so it can't be faked that way.
- `assemble` never deletes: assembling a smaller tier onto a stick that holds a bigger tier's models leaves them (it logs which), and run.sh uses them.
- Untested exits: timeout (needs hours of runtime or a test-only knob), USB read-only/full refusal, SIGHUP. The code paths are short; each records an explicit status if hit.
- The macOS path (sysinfo; membw only if a compiler exists) is untested: no Mac here.
- The wall clock on an offline box may be wrong; durations use `/proc/uptime`, timestamps are only as good as the clock.
- The background copy can overlap the first benchmarks (idle priority, and `env.txt` records it). Phase 2-3 numbers may be a few % low on a box where the copy competes; `env.txt` says which steps overlapped it.
- Throttling or background load during a bench is recorded (loadavg before each bench, process list in sysinfo) but not prevented.
- GPU hang/reset and VRAM taken mid-step by another program are untested; each ends the step `failed` or `timeout` with stderr kept.
- 3-03's partial-failure check matches the two failure messages in llama.cpp's perf loop (`failed to allocate`, `graph_compute failed`, read from its source); a failing perf case wasn't reproduced here.
- If the lab box has no Vulkan driver for the GPU (Ubuntu's `mesa-vulkan-drivers` not installed), every GPU step is skipped; the kit does not carry its own driver. sysinfo's `vulkan.txt` will show it, and the next kit can bring one.
- The Polaris check at home is an approximation: a newer AMD GPU with fp16, integer dot product, cooperative matrix and bf16 turned off in llama.cpp. Polaris-specific driver bugs only show up in 3-02 on the lab box.

# Lab kit design

**Invariant:** tests run in a fixed priority order (phases 1-4, 4b), and every planned step ends with exactly one recorded outcome (`ok`, `skipped` + reason, `absent` + reason, `failed`, `timeout`, `interrupted` or `crashed`), and its raw output sits next to it. Nothing is silently dropped, and the kit never changes the lab machine beyond `/var/tmp/perseus-kit-local` and the GPU's performance level while a phase 4b step pins it (always put back: see Phase 4b).

| Exit | Behaviour | Test |
|---|---|---|
| done | `status=ok`; summary.txt + `FINISHED` marker written | local e2e run |
| failed | `status=failed`, exit code in `status.json`, stderr kept; run continues with the next step | e2e: corrupted model copy fails its stage step |
| skipped | `status=skipped` + reason (single NUMA node, no sudo, not enough RAM, model not on USB) | e2e on this 1-node box |
| timeout | `timeout` exit 124/137 → `status=timeout` | untested (see Known gaps) |
| cancelled (Ctrl-C) | the signal reaches the benchmark itself (`timeout --foreground`, same process group), current step → `interrupted`, summary written, lock released, exit 130 within seconds; rerun repeats that step | e2e: SIGINT to the process group mid-step (2-00b's self-test); stops < 20 s, nothing of it left |
| terminal closed (SIGHUP) | same as Ctrl-C | shares the trap; not separately tested |
| crash / power loss / OOM kill mid-step | `started` marker without status → next run marks it `crashed` and does **not** retry it (so one bad step can't wedge every rerun); `--retry-failed` reruns it. A dead runner left as a zombie doesn't hold the lock | e2e: kill -9 the process group mid-step, with and without an init reaping zombies |
| retried | `--retry-failed` reruns failed/timeout/crashed; ok/skipped never rerun | e2e |
| duplicated (two runs at once) | `mkdir` lock with host+pid; live owner → refuse; stale owner → atomic `mv` takeover, one winner | e2e: second run while first is live |
| paused (`run.sh pause`, or `p` in the run window) | flag file (`p` again removes it); the runner finishes the current test, then stops cleanly (exit 0, summary written); a stage step waiting on the copier ends `interrupted` and reruns | e2e: pause mid-bench |
| stopped (`run.sh stop`) | SIGINT to the runner's process group (recorded in the lock) = Ctrl-C | e2e |
| time limit (`--for TIME`) | no new test starts after TIME (`95` = minutes, `90m`, `8h`, `1h30m`; 0, empty, fractions and over a week are usage errors, exit 2) (uptime clock, immune to a wrong wall clock); the running one finishes; the banner's cutoff is that deadline, not one counted from after setup | e2e with `--for 1` (a 20 s minute: `PERSEUS_MINUTE_S`); e2e-tty (a) parses each form |
| screen (`lib/ui.sh`) | run.log always gets the plain lines. A terminal gets phase rules, a glyph and `[n/total]` per step, and a live timer: a background subshell redrawing the running step's line each second. The runner kills it when the step ends and in the Ctrl-C/stop trap before printing "Stopped." (the stopped step keeps its line); it polls the runner's pid and state, so a kill -9 of the runner alone ends it within a second even while the runner is an unreaped zombie. Builtins only, one `sleep` a second, since it shares the box with benchmarks. At a terminal that wait is a one-second `read` of one key instead (`p` pause, `s` status, `l` the step's last output, `m` CPU/RAM/GPU, `?`); each prints above the timer's line. The read changes the terminal's modes: bash puts them back when the timer is killed (SIGTERM, deliberately untrapped), and `ui_tick_stop` restores the modes saved at start; a kill -9 of the whole run can leave the terminal without echo (`reset`). No timer on a terminal narrower than its line (a wrapped redraw leaves a trail) or TERM=dumb; on a resize (SIGWINCH) the width is re-read (`stty size </dev/tty`), a running timer that no longer fits clears its line and stops, and the next step re-checks; colour only without NO_COLOR and TERM=dumb; ASCII glyphs outside UTF-8 locales; a pipe or file gets the plain lines | e2e-tty: pty runs (colour, NO_COLOR, LANG=C, 40 columns, narrowed to 40 mid-step, setup slower than --for), pipe, status mid-step, stop mid-step (no redraw after "Stopped.", nothing left), kill -9 of the runner alone, and under a parent that never reaps it; stub-4b (p): each key's view in a pty, `p` sets and clears the flag |
| background copy | copier in its own session at idle CPU/IO priority (the runner records its pid before any step runs, so a stage step never copies alongside a copier that hasn't started yet), copies in plan order, sha256 → `.ok`/`.bad`/`.nospace`; killed with the runner; a copier orphaned by a crash is killed on the next start and its `.part` removed; each bench records whether a copy was running (`env.txt`) | e2e: copy mode, stop mid-copy, kill -9 mid-copy; e2e-diag (b): copier delayed 3 s at start, the resumed run's first stage step waits for it |
| reordered | steps have fixed ids; resume keys on the id, not position | by construction |
| USB moved to another machine | lock owner host differs → treated as stale; results dir is per host | by construction |
| identity change (sudo vs not) | local cache path fixed (`/var/tmp`), not `$HOME` | by construction |
| wrong CPU build | variant picked from `/proc/cpuinfo` (or forced with `PERSEUS_VARIANT`, validated), then proven with a tiny real benchmark; SIGILL → next older build | QEMU (`build-kit.sh test`): emulator traps each newer extension, each build runs every shipped kernel on its oldest target CPU, a newer build traps. The step-down loop itself is untested |
| perseus kernels wrong on the real CPU | steps 2-00 (SSSE3, multi-column and repacked-IQ3_S kernels), 2-00b (tiled matmul), 2-00d (IQ3_S repack through ggml's graph API) and 2-00f (Flash-Next formats q6_K/q5_K/iq4_nl/q2_0, plus q4_1) run the self-tests on the lab box first; a failure is recorded like any step, so the CPU-side Flash-Next numbers after it (its routed experts run on these kernels) are known-suspect | `kernels/test_ssse3_kernels.c`, `kernels/test_fn_kernels.c` (both mutation-tested), llama.cpp's `test-tiled-mulmat`, `kernels/test_repack_mulmat.c` (fails when the repack is off), QEMU Penryn/Nehalem |

| model not on this USB (diag kit; core kit's Flash-Next) | `status=absent` + reason. Not final: every resume re-evaluates it, so a USB re-assembled with a bigger tier runs it. Only the USB counts (a local copy from an earlier, bigger kit doesn't), so a diag kit never runs model tests. `status` counts them per phase ("need models not on this USB"); summary.txt lists each one plus their total | `kit/test/e2e-diag.sh` (b): diag run paused after 2-05, USB re-assembled with core, resume runs 2-01..2-05. Fails when `absent` is final like `skipped` |
| diag kit (no models) | phases 1-3 run (the GPU checks need no model); every model step ends `absent`; FINISHED and DONE (with the absent count); no background copier and nothing in the local dir but `bin/`; the startup line says diagnostics-only, ~10 min. With no tiny model, one trial of the kernel self-test proves the CPU build instead of a tiny benchmark | e2e-diag (a), on a FAT32 image mounted by `udisksctl` |
| USB re-assembled after a FINISHED run | FINISHED is final: the next run starts a new results folder and repeats phases 1-3 (~15 min) before the model tests | by construction (`pick_run_dir`) |
| FAT32 USB | `assemble` refuses it when a model file is over 4 GB (full: Flash-Next) and allows diag and core. udisks mounts vfat with `showexec` (udisks2 2.11.2's builtin `vfat_defaults=uid=$UID,gid=$GID,shortname=mixed,utf8=1,showexec,flush`), so nothing on the stick is executable (exec gives 126, chmod is a no-op); run.sh only executes its local copy of `bin/` | e2e-diag (a) on a FAT32 image mounted by `udisksctl` |
| damaged model copy | sha256 checked after copying to local disk; mismatch → `.bad`, model steps skip | e2e: one flipped byte in the USB copy |
| RAM too small for a model | skipped with the numbers, never started (avoids OOM-killing the box) | e2e-gpu: Flash-Next (75.8 GB) on a box with less free RAM |
| hidden memory use beyond the weights | completion steps pass `-c` (the default is the trained context: 262k on Qwen3.8, ~17 GB of KV on the 27B); llama-bench sizes its own context | found with Qwen3.8-27B + MTP head (no longer in the kit) in a 12 GB cgroup: OOM-killed twice without `-c 1024` |
| started without sudo | at a terminal with models on the USB: "Continue without sudo? [y/N]" before anything starts (no results folder, no lock); default no exits 1 with the sudo command and the same arguments. Not at a terminal (nohup, pipe): a warning, and phase 4b's clock and profile steps end `skipped` | stub-4b (o), in a pty |
| started wrong: another shell, a trimmed PATH, lib/ unreadable | `sh run.sh` (dash; bash in POSIX mode) re-runs itself in bash. The system's bin directories are appended to PATH first, so the re-run finds bash too (a sudoers `secure_path` can leave out `/usr/bin`). A `lib/*.sh` that can't be read or was cut short (each ends by setting `LIB_END` to its name), or a missing core command, stops it with one message naming the file or command, before any test. bash goes on past a failed `.`: without this, every test ends `run_step: command not found`, the symptom run 3 showed at the lab | stub-4b (s); a 24.04 container with `sudo sh` and `secure_path=/snap/bin` |
| USB read-only / full | refuses to start with a message | untested (see Known gaps) |

Copies others hold: the page cache holds model files between steps (deliberate); `/var/tmp/perseus-kit-local` holds binaries + models until `run.sh clean` (a diag kit puts only `bin/` there). Model copies left there by an earlier kit are not used unless the USB carries that model too.

## GPU (phase 3) and Flash-Next (phase 4)

The lab box has an AMD RX 580 (Polaris, PCI `1002:67df` rev e7). Flash-Next's per-token bytes are mostly its always-read part (attention, shared experts, router: ~3.8 GB/token in the IQ3_XXS build) while its routed experts are ~0.84 GB/token, so the plan is llama.cpp's MoE split: the always-read part on the GPU, routed experts in RAM on the CPU's SSSE3 kernels.

**Invariant:** every GPU step runs on the one device the probe (3-01) picked and names it; no GPU step can make a CPU-only result wrong or missing, and every step still ends with exactly one recorded outcome.

| Exit | Behaviour | Test |
|---|---|---|
| GPU found | 3-01 lists Vulkan devices with the kit's own build and picks the first discrete one (llama.cpp's default list holds only real GPUs, no software rasteriser; of those, the first with `uma: 0`, so an iGPU never counts); records llama.cpp's name for it (`VulkanN`, shape-checked before sourcing) and VRAM in `$RUN_DIR/gpu.env`, its full name in `gpu-name.txt`; every later GPU command selects it with `-dev`/`-b VulkanN`, so a missing device is an error, never a silent CPU run. Not `GGML_VK_VISIBLE_DEVICES`: that indexes Vulkan's raw device list, which can differ from llama.cpp's numbering when a software rasteriser or filtered device comes first | e2e-gpu (a): RX 9070 XT + Ryzen iGPU visible, picks the 9070 XT, bench reports it; (e) with the GPU gone, the old `GGML_VK_VISIBLE_DEVICES=0` selected Mesa's llvmpipe (raw device 0) and its runs passed as GPU results |
| GPU gone or changed after 3-01 (driver removed, device added, resume on another day) | each GPU step re-lists devices (bounded like every command: 120 s, then `timeout`) and fails unless `VulkanN` still has the recorded name. `test-backend-ops` exits 0 when the named backend is missing (it skips it), so its output must show `Backend VulkanN: OK` and more than 0 cases (test) or timed ops (perf), else the step fails | e2e-gpu (e): probe with the GPU, resume without it → 3-02..3-05 `failed`; passed 3-02 on zero cases before this check |

It writes them, with their weight types, to `MODEL.txt.builtin`; 3-02 runs llama.cpp's own cases for exactly those (they use distinct values, compare sets, or valid inputs), so every op type a model uses is checked one way or the other. ## Phase 4b: where Flash-Next's CPU+GPU time goes

Run 2 decoded Flash-Next at 278 ms a token on CPU+GPU against a ~85 ms bandwidth ceiling (GPU part ~30 ms, CPU experts ~45-55 ms). 4b splits that time up and A/Bs three free knobs:
- `novis`: `GGML_VK_DISABLE_HOST_VISIBLE_VIDMEM=1`. ggml-vulkan asks for CPU-visible VRAM first (`ggml-vulkan-buffers.cpp`, "use rebar if available"). Without Resizable BAR that is 256 MB on the lab box, and the rest spills to system RAM read over PCIe 2.0: run 2's op bench had 8 matmuls at 1-3 GB/s where the same shapes ran at 120-145.
- `dpm-high`: the GPU's clocks pinned (`power_dpm_force_performance_level=high`). It idles while the CPU runs each layer's experts, and its memory clock idles at 300 MHz.
- `dio`: weights read into RAM with direct I/O instead of mmap (llama.cpp warns that CPU tensor overrides with mmap are slower).

Every GPU step places the same way, `-ngl 99 -ot exps=CPU`: all but the routed experts on the GPU (5.4 GB of 8). Not `-fit`, because llama-bench frees and reloads the model for every test when fitting, and a fixed split keeps the A/B comparable. 4b-05 picks the fastest decode of 4b-01..04, and the later steps run under that config.

**Invariant:** the GPU's performance level differs from its pre-run value only while a 4b step that pins it runs its benchmark. Every way out of that step puts it back (at the latest when `run.sh` next starts, or on reboot), and no 4b step leaves a process behind.

Ordering rule: a step's own prerequisites (model on this USB, GPU, tools) decide its outcome before its config acts. `step_cfg` only records the config; the clocks are pinned in `note_env`, which every timed step calls right before its command. So a step that can't run never touches the GPU, and a missing model stays `absent` (rerun later), not a final `skipped`. A pinned config whose step never reached `note_env` fails the step instead of reporting unpinned numbers as pinned.

## Known gaps
- A step whose command itself exits 3 is recorded as `skipped`: `skip()` and such a command share the exit code. `absent` uses a marker file, so it can't be faked that way.
- `assemble` never deletes: assembling a smaller tier onto a stick that holds a bigger tier's models leaves them (it logs which), and run.sh uses them.
- Untested exits: timeout (needs hours of runtime or a test-only knob), USB read-only/full refusal, SIGHUP. The code paths are short; each records an explicit status if hit.
- The macOS path (sysinfo; membw only if a compiler exists) is untested: no Mac here.
- The wall clock on an offline box may be wrong; durations use `/proc/uptime`, timestamps are only as good as the clock.
- The background copy can overlap the first benchmarks (idle priority, and `env.txt` records it). Phase 2-3 numbers may be a few % low on a box where the copy competes; `env.txt` says which steps overlapped it.
- Throttling or background load during a bench is recorded (loadavg before each bench, process list in sysinfo) but not prevented.
- GPU hang/reset and VRAM taken mid-step by another program are untested; each ends the step `failed` or `timeout` with stderr kept.
- 3-03's partial-failure check matches the two failure messages in llama.cpp's perf loop (`failed to allocate`, `graph_compute failed`, read from its source); a failing perf case wasn't reproduced here.
- If the lab box has no Vulkan driver for the GPU (Ubuntu's `mesa-vulkan-drivers` not installed), every GPU step is skipped; the kit does not carry its own driver. sysinfo's `vulkan.txt` will show it, and the next kit can bring one.
- Phase 4b: if a run is killed mid-pin and the kit never runs again, the GPU stays at `high` until reboot (more power and heat, no harm to results). A `skipped` step is final, so steps skipped for want of 4b-05's pick don't rerun when `--retry-failed` later fixes 4b-05.
- Phase 4b's wiring is tested with stub binaries and a fake sysfs (`test/stub-4b.sh`); the knobs' real effect, `perf` on the lab's Ubuntu and the Vulkan timer's output are only seen on the lab box.
